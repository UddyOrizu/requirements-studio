## S01 — Send the document request through the client portal (accepted)

An agent sends the checklist through the existing client portal as soon as the client record is created, and documents come back there instead of by email.

**Why:** Documents are gathered by email today, and the portal already exists but isn't used for KYC.

> "We have a client portal but don't use it for KYC yet" — T10
> "gathers ID documents by email" — T0

**Human control:** None needed: the request uses an approved template.
**Risk:** Clients unused to the portal may need a one-off email with the link.

## S02 — Automate document reminders (accepted)

Reminders go out automatically through the portal on day 5 and every 3 working days after, stopping when documents arrive.

**Why:** Chasing is the biggest single cost today: about 30 minutes of emails per client.

> "chasing about 30 minutes per client in emails" — T16

**Human control:** Engagement Manager is still told after 10 working days (existing exception).
**Risk:** Over-chasing a client who has replied by email; reminders stop on any upload.

## S03 — Verify IDs through the e-ID service API (accepted)

An agent submits each ID to the e-ID verification service automatically. Documents that fail go to an analyst's queue.

**Why:** IDs are checked by hand on the e-ID website today.

> "Checking IDs by hand takes about 20 minutes" — T16
> "checks IDs on the e-ID verification website" — T10

**Human control:** Human queue: failed checks go to an Onboarding Analyst.
**Risk:** Depends on the e-ID service offering an API (to confirm with James).

## S04 — Screen automatically, analyst reviews possible matches (accepted)

An agent screens the client and every director in one batch through the screening tool's API. An analyst only reviews possible matches.

**Why:** Screening takes about 25 minutes because every director is searched separately, and the tool has an API.

> "screening about 25 because every director is searched separately" — T16
> "The screening tool has an API for single and batch checks" — James Patel, q_intake_01

**Human control:** Human review: an Onboarding Analyst confirms or clears every possible match before the case moves on.
**Risk:** The match-score threshold decides how many cases reach an analyst (needs setting).

## S05 — Apply the risk rating rule automatically (accepted)

The rating rule you described runs as code on the screening result and client country, with the reason recorded.

**Why:** The rule is explicit and needs no judgement, so a person applying it by hand adds time but not value.

> "Any sanctions match or a PEP makes it high risk" — T6
> "the rating takes 10" — T16

**Human control:** Approval gates for medium and high risk stay as they are.
**Risk:** Rule changes must go through change control.

## S06 — Write the outcome to the CRM and file the evidence automatically (accepted)

An agent writes the rating, approvals and status to the CRM and files the documents and screening results to the client file.

**Why:** The outcome is typed into the CRM by hand today.

> "typing it all into the CRM and filing takes another 15" — T16

**Human control:** None needed: every write is logged as evidence.
**Risk:** CRM outages need a fallback.

## S07 — Auto-approve medium risk when the only flag is the country (rejected)

Medium-risk clients flagged only for a high-risk country, with no adverse media, are approved automatically.

**Why:** About a third of medium-risk cases may be country-only; automating them would cut analyst approvals further.

> "Adverse media or a high-risk country makes it medium" — T6

**Human control:** Weekly sample of auto-approved cases reviewed by an analyst.
**Risk:** Removes a person's judgement from some medium-risk decisions.
**Benefit:** Fewer analyst approvals for medium risk (volume not yet known)
**Decision reason:** Medium-risk clients still need a person's judgement, even if the only flag is the country.
